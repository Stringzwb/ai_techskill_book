# 代码规范和要求

## 通用注释要求

1. 注释必须始终与当前代码行为保持一致。修改代码、配置、接口或业务逻辑时，必须同步检查并更新相关注释
2. 禁止保留已经失效、与实际功能不符或可能误导维护人员的注释

## 凭据与提示词安全

1. 账号、密码、Token、私钥、对象存储密钥、数据库连接串和模型 API 密钥只能存放在服务器受限环境文件、操作系统密钥链或批准的密钥管理系统；Git 只提交 `.env.example` 占位模板。
2. 不得在源码、日志、部署文档、截图或 AI 提示词中写入真实敏感值。日志禁止记录认证头、正文、完整环境文件和第三方 API 响应。
3. Kafka 消息只传递文档主键、正文版本和任务类型，不传递 Markdown 正文或任何凭据。
4. LangChain4j 仅通过 OpenAI 兼容配置调用模型，默认关闭；`OPENAI_API_KEY` 只能从服务器环境或密钥链注入。

## 凭据与提示词安全

1. 账号、密码、Token、私钥、连接串中的凭据、对象存储密钥和生产环境 `.env` 文件均属于敏感配置。真实值只能存放在服务器受限环境文件、操作系统密钥管理工具或团队批准的密钥管理系统，Git 只提交 `.env.example` 占位模板。
2. 不得在源码、测试固件、文档、部署日志、截图、终端历史或 AI 提示词中写入真实敏感值。日志只记录操作结果、服务状态和脱敏后的配置键名，不记录环境文件全文、认证头或原始远端输出。
3. 可以在已获授权的范围内通过 SSH 连接服务器进行只读检查、部署和故障处理。连接参数从本地未跟踪配置读取，认证信息从钥匙串或受限密钥存储读取；禁止通过提示词或命令从文档中提取、转发或回显密码。
4. 向 AI 提交运维任务时，只提供目标、项目路径、授权范围、允许的操作和验收标准。例如“使用既有安全连接对应用服务器执行只读健康检查”。不要粘贴密码、Token、完整环境文件、原始 SSH 会话日志或内部代理执行记录。
5. AI 执行服务器任务前先说明影响范围；默认使用只读检查。涉及部署、迁移、重启、删除或修改生产数据时，必须在任务中明确授权并按部署流程执行。

## 后端要求

1. mybatis和mybatis-plus公用，简单查询使用plus，复杂查询直接写sql

2. 实体类采用lombok都注解简化 每个字段要有注释

3. 每个类有类注释 方法有方法注释

4. 包结构：

   外层为多个模块（逻辑上的模块即可，不需要为maven模块）

   内部包命名 controller service mapper domain（require，request，entity，enums 文件命名时也要遵守类似写法） utils common config

5. 每个application的配置要有注释

## 数据库要求

1.每个数据库表必须添加 createtime updatetime createby updateby deleted（逻辑删除，0正常，1已删）以及至少三个冗余字段

2. 上述字段添加基础继承类和自动审计（createby等可由登陆系统实现后再开发）
3. 每个ddl必须有字段注释和表注释

## 对象存储要求

1.业务模块只能调用 `storage` 通用模块，禁止直接创建 S3 客户端；Endpoint、AccessKey、SecretKey、Bucket 等真实配置只能通过环境变量注入，不得提交到 Git

2.对象键统一为：`<环境>/<业务>/<yyyy>/<MM>/<归属ID>/<UUID>.<扩展名>`，例如 `prod/avatar/2026/08/123/uuid.webp`；禁止使用用户原始文件名、连续斜线、相对路径或包含敏感信息的目录名

3.业务目录使用小写英文并按需登记，当前已登记 `avatar` 和 `article`；`article` 仅保存私有 `text/markdown` 正文，单个对象最大1MB，由文档存在期间持续保留并在正文替换或文档删除后清理；新增 `attachment`、`export` 等目录前必须先明确访问权限、文件类型、体积限制和生命周期

4.存储桶默认保持私有。数据库保存稳定对象键和受控业务访问地址，不保存临时签名 URL；文件访问由后端鉴权代理或按业务生成短期签名地址，禁止为了单个业务直接开放整个存储桶

5.所有上传必须同时校验体积、声明 MIME 和真实文件特征，使用服务端生成的扩展名和 UUID；下载响应必须使用服务端可信媒体类型，禁止透传用户提交的路径和媒体类型

6.对象替换采用“先上传新对象 -> 更新业务记录 -> 事务成功后删除旧对象”的顺序；数据库更新失败时清理新对象，异步清理失败需记录不含凭据的安全日志并支持后续巡检

7.对象元数据只保存业务类型、归属标识等非敏感信息。日志不得记录 AccessKey、SecretKey、签名 URL、文件正文或供应商完整错误响应

8.生产发布前必须验证配置、写入、受控读取和删除闭环；验证对象必须放在对应环境的 `system/smoke` 或实际业务测试路径并在验证后清理

## 部署要求

1.前后端项目的部署要有一次性部署文档或脚本，暂时采用systemctl的方式部署，后续可能改为docker部署
2.每次部署后在 /docs/deploy中填写部署日志
3.所有修改必须先在本地完成并通过测试，再提交并推送到 Git；禁止直接修改服务器中的项目源码
4.当前生产环境只部署 main 分支，部署顺序固定为：本地修改与验证 -> 提交并推送 Git -> 服务器执行 `git pull --ff-only origin main` -> 构建 -> 数据库迁移 -> 重启服务 -> 健康检查
5.数据库结构变更必须使用版本化迁移脚本；执行前检查现有结构和数据，生产环境变更前保留结构备份，并保证迁移可重复检查和可回滚
6.部署前保留上一版后端 JAR 和前端静态文件，部署失败时优先恢复上一版产物
7.涉及登录、会话或个人信息的生产环境必须启用 HTTPS；会话 Cookie 必须开启 Secure、HttpOnly 和 SameSite，禁止通过明文 HTTP 承载真实用户登录
8.HTTPS 证书必须配置自动续期和续期后的 Nginx 重载，并在部署验证中检查证书有效期和续期定时器

## Git 提交规范

1.提交格式统一为：`<type>(<scope>): <summary>`

2.type 可选值：

- `feat`：新增功能
- `fix`：修复缺陷
- `refactor`：不改变功能的代码重构
- `docs`：文档修改
- `test`：测试新增或调整
- `build`：构建、依赖或部署调整
- `chore`：其他维护工作

3.scope 使用简短模块名，例如 `auth`、`user`、`frontend`、`deploy`；同时涉及多个模块时可省略

4.summary 使用简洁中文说明结果，不加句号，建议不超过 50 个字符，例如：`feat(auth): 新增密码登录和Redis会话`

5.每个提交只包含一个明确目标，提交前必须检查 `git diff`，不得提交密码、Token、真实环境配置、构建产物和无关文件

6.main 分支必须保持可构建、可部署；多人协作或较大功能使用 `feature/<功能名>` 分支，经检查后合并到 main

7.推送前至少执行与改动相关的后端测试和前端构建；测试失败不得推送或部署
